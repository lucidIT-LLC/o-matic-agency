# Factory construction

Read this when the operator asks to create, set up, or convert a factory. The live procedure is on the server. Do not recite interview questions from memory.

## Contents

- Install
- Four layers
- After

## Install

Use the `/install-factory` command where the host ships it. Otherwise ask a server administrator to run the install. Never run commands on the server host yourself. Never edit server configuration.

Follow the command as written: plan, the operator's own yes, apply with the connection and the grant so the factory is reachable in the same run, then a fresh `startup` on the new connection. A new factory reads DEGRADED with governance unknown only. Any other reason is a defect to report.

## Four layers

Read the construction procedure live from the server's operating guide, top down. Each layer is answerable only after the one above exists.

1. **Purpose.** Objectives, in the operator's own words. Draft wording only on request. Never originate the intent.
2. **Evidence.** Key Results that can return red, or an honestly declared owed instrument.
3. **Services.** What the factory produces, and what it explicitly is not.
4. **Roster.** Who does the work, with agreement state and live authority. Omit the authority half and work stays assigned to roles that cannot perform it.

Then re-trace what sits underneath: procedures, policies, open tasks, routing. Each item names the Objective it serves, or it is retired. The trace has to be argued, not merely labeled.

Ask about incidents and costs. Asking for a value-word produces nothing usable. Stop when an answer grades strong.

Result words are baseline recorded, staged, accepted for burn-in, promoted, or blocked. READY is the startup packet's measured state and is never a conversion verdict. Convert by preserve, adapt, and add. A factory pulls a conversion. This pack never pushes one into another factory.
