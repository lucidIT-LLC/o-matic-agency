# Factory Governance Repair

Use when a live finding identifies a specific governance defect and the
operator has authorized its repair. Preserve stronger working local controls.

## Resolve authority before designing a repair

1. Start the target through the o-MATIC Server; retain its returned connection,
   factory identity, tenant, state, and verbatim state reason.
2. Read `omatic_guide(topic="blueprint")`, then the relevant per-document
   topics it lists. The Blueprint shipped with the installed Server release
   is authoritative (decision #708). Former Commons Blueprint copies are audit
   history, even if their catalog rows still say active. A cached skill or
   legacy factory document does not override the released contract.
3. Use the released Certification Authority and the target's live checklist
   to select acceptance requirements. Do not revive retired floors or turn an
   optional hardening proposal into a certification prerequisite. Keep READY,
   checklist conformance, host acceptance, and promotion distinct.
4. For release catch-up, use the current install/upgrade guide and the supported
   scoped plan, rehearsal, apply, and readback path. Honor the command's actual
   authorization requirements. Do not substitute a custom shared Server patch
   for a release migration or overwrite a differing local object automatically.
5. Name the failing behavior, governing clause, exact control to change, and
   the normal-role refusal and legitimate-operation tests before mutation.
   Resolve conflicting authority before changing a durable control.

Probot owns sequencing and the session record. Data owns factory database
repair and verification; Carver owns application and repository changes;
Fred records custody. Route independent review where the current contract or
operator requires it. Role names alone do not grant credentials or authority.

## Contract alignment

An implementation repair that preserves the released contract does not need a
cosmetic Blueprint rewrite. Record why no contract amendment was necessary.

If the contract itself must change, amend the Blueprint source repository,
version the change, and ship it through the normal release process. Never edit
an audit-only Commons copy as though it were the live Blueprint. Change any
applicable companion procedure or program record in its own documented role;
do not duplicate Blueprint text across records. Preserve revision history.

Verify the released version and serving text of every authority actually
changed. Record its version, digest, target control, and behavioral proof in
the target factory's existing change record. A source edit alone is not a
claim that the installed release or retrieval corpus has changed.

## Repair invariants

- **Session lifecycle:** distinguish a blank open session from an incomplete
  close. Prove incomplete-close refusal and a complete close/readback through
  the normal factory role. Preserve the actual roster/client identity model;
  do not invent a separate credential requirement for a persona.
- **Tenant isolation:** filter and join tenant-owned relations on tenant_id.
  Do not create another tenant or touch another factory without authorization.
  Shared doctrine follows its own published scope.
- **Readiness:** use current-session measured evidence for applicable connectors.
  UNTESTED is not a probe. Critical failures block dependent work; unavailable
  host features and noncritical failures retain their actual scope and fallback.
- **Policy and SOP coherence:** preserve the active Policy's approval and
  fallback boundaries. A review fallback must not become a publication bypass.
- **Memory and retrieval:** derive lifecycle and authority from source evidence.
  An archived authority label alone does not prove that a source is retired.
  Refresh derived records through their governed paths, verify source and
  catalog integrity, and exercise task-appropriate governed retrieval. Record
  the actual mode and weights status rather than imposing an obsolete universal
  vector-traffic floor.
- **Proof:** test both refusal and a legitimate operation. Where production
  firing evidence is required, fix the corpus and known labels before scoring;
  a false positive is a defect, not a successful refusal. Keep superseded proof
  and its correction recoverable.

## Execution and verification

Use the o-MATIC Server MCP surface for normal database work. The factory's
own database login owns its objects: authorized database-local DDL and DML use
factory_query. Reserve factory_owner_ddl for provisioning that actually needs
its privileges, following its live confirmation and audit contract. Never
silently widen the operator's factory, host, or external-action scope.

Store transactional migration and rollback evidence. Never edit an applied
migration; put a correction in a new file. Protect credentials from source,
logs, and session records.

After the repair, read back deployed definitions and affected rows, rerun the
failing behavior and legitimate path, and run the released checks affected by
the change. Re-read startup state separately from acceptance. Record source
custody, installed release, checklist version/generation, results, and remaining
unmeasured or blocked paths. If the session ends, close it through the target's
current session procedure and read back the persisted record.

Keep chat brief; put detailed evidence in the target change record and name it.
