# Codex Adapter

Install the Agency plugin at `../../.codex-plugin` so Codex discovers the L1
skills in `../../skills/`. Each core skill carries `agents/openai.yaml` and a
local SVG asset so supported Codex desktop surfaces can display its name, color,
and icon. This metadata identifies a skill; it does not turn a skill into a
subagent or guarantee a host-owned avatar outside the skill UI. Load the compact resident core kernel contract before
or alongside any direct core-role or specialist invocation: Probot retains
orchestration, Fred retains custody awareness, and Data retains evidence and
retrieval boundaries. The canonical role contract and conformance suite remain
adjacent for release verification.

For L2, use a separate host agent harness only after it has an explicit workflow
record in `factory.agent_runtime_contracts`, a least-privilege allowlist, owner,
approval policy, rollback plan, and passing evaluation. A Codex skill alone is
L1 behavior, not an autonomous deployment.

## Startup presentation and persistent orientation

On startup, discover the callable native O-Matic Server registry before
declaring a host publication gap: a compact or initially rendered palette is
not proof that `startup` is unavailable. Once `startup` is callable, render its
native packet with `agency/scripts/format-startup-card.mjs`. The renderer is
presentation-only: it never derives state, invents severity, or performs
another database call. A successful native startup call proves the O-Matic
Server was exercised and reachable; server-declared `connector_readiness` is
rendered as connector coverage not probed, never as a factory fault.
For the rest of the task, append `formatFactoryFooter()` to each final response
using that same packet. It must identify the factory and state; retain any
server-declared `unmeasured` field. Refresh the packet only after a new startup
or an operation that measures a field again.
